Ciblage précis du responsable identifié (boucle fermée)

Corrige un bug de fond : le transcript envoyé à l'IA n'avait jamais de repères "Intervenant N", donc les rappels et notifications visaient tous les participants d'une session, jamais spécifiquement la bonne personne — même quand la reconnaissance de voix récurrente l'avait identifiée.

§ Le besoin

Limite déjà documentée deux fois (rappels d'engagements, boucle fermée) : Engagement.responsable n'était qu'un label de diarization, jamais lié à un vrai compte. En creusant pour la fermer une fois la reconnaissance de voix récurrente disponible, un bug de fond est apparu : CompteRenduService envoyait à l'IA un texte concaténé sans aucune étiquette de locuteur, alors que la consigne lui demandait justement de réutiliser des repères "Intervenant N" — l'IA semblait donc inventer des noms trouvés dans le contenu de la conversation plutôt que de reprendre une étiquette qu'elle n'avait jamais reçue.

§ Les décisions de conception

  • Étiqueter le transcript avant l'IA, pas après — ConstructeurTranscriptLabelise (nouveau, core.transcription) construit un texte où chaque ligne commence par une étiquette : vrai nom si identifié, sinon repère générique. Utilitaire du moteur commun, pas d'Entreprise.
  • Repère local à un seul appel, jamais une identité globale — regroupement par (numeroSequence, locuteur), cohérent avec la limite déjà documentée dans IdentificationLocuteurService (Azure renumérote les locuteurs par appel HTTP).
  • responsableUtilisateurId résolu automatiquement — ConstructeurTranscriptLabelise.Resultat renvoie une map étiquette→utilisateur ; quand l'IA reprend une étiquette connue, le lien est résolu sans aucune action utilisateur.
  • Consigne IA durcie — "reprends EXACTEMENT l'étiquette... n'invente jamais un nom mentionné ailleurs dans le contenu" : nécessaire car un vrai nom ressemble à une mention légitime dans une phrase.
  • Repli sur le comportement historique — ciblage précis seulement quand responsableUtilisateurId est connu, sinon tous les participants comme avant : aucune régression pour les engagements déjà existants.

EngagementService / RappelEngagementService — resoudreDestinataires

private List<String> resoudreDestinataires(Engagement engagement) {
    if (engagement.getResponsableUtilisateurId() != null) {
        return utilisateurRepository.findById(engagement.getResponsableUtilisateurId())
                .map(Utilisateur::getEmail).map(List::of)
                .orElseGet(() -> sessionService.resoudreEmailsParticipants(engagement.getSessionId()));
    }
    return sessionService.resoudreEmailsParticipants(engagement.getSessionId());
}

Note — même méthode dupliquée à l'identique dans les deux services : pas d'abstraction commune pour deux appelants seulement.

§ Comment on a vérifié en conditions réelles

Vérifié avec de vrais appels Azure OpenAI (pas de mock, pas de factice) : un locuteur enrôlé et identifié via la reconnaissance de voix récurrente, l'IA réutilise correctement son vrai nom comme étiquette de responsable (pas un nom inventé à partir du contenu de la conversation) ; dans une session à deux participants, un seul email de notification part au responsable identifié.

Confirmé : l'autre participant ne reçoit rien — la boucle est réellement fermée sur la bonne personne.

§ Limites connues, assumées

  • Repère local à un seul appel IA — un locuteur non identifié parlant dans plusieurs chunks peut recevoir plusieurs étiquettes différentes, aucun recollement inter-chunks.
  • Dépend entièrement de la reconnaissance de voix récurrente — sans profil enrôlé, comportement identique à avant cette brique.
  • Pas de test dédié pour ConstructeurTranscriptLabelise — couvert seulement indirectement via CompteRenduServiceTest.
  • Duplication volontaire de resoudreDestinataires entre les deux services.

§ Pour reprendre seul

  • Chemin de bout en bout : CompteRenduService.obtenirOuGenererCompteRendu → ConstructeurTranscriptLabelise.construire → GenerateurCompteRenduAzureOpenAI (reprend l'étiquette exacte) → ActionCompteRendu.responsableUtilisateurId résolu → EngagementService.creerEngagements → resoudreDestinataires (ciblé si connu, sinon repli historique).
  • Le chantier "rappels + boucle fermée + ciblage précis" côté engagements est maintenant complet au sens du master prompt. Prochaine direction retenue après cette brique : séparation École/Entreprise en modules distincts.
