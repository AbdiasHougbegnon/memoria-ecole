§ Le besoin

Jusque-là, TranscripteurAzureSpeech appelait l'API de reconnaissance "courte durée" d'Azure Speech — faite pour transcrire une voix. Elle ne sait pas distinguer plusieurs personnes qui parlent dans le même enregistrement. Pour un transcript de réunion ou de cours utile, il faut savoir qui a dit quoi, pas juste ce qui a été dit.

§ Pourquoi il a fallu chercher avant de coder

Un piège déjà rencontré une fois avec Azure OpenAI : une API qui ressemble à ce qu'on attend, mais qui ne fonctionne pas comme les tutoriels génériques le laissent penser. Plutôt que de deviner le format et écrire du Java dessus tout de suite, test direct au curl, en dehors de toute application.

1

Premier essai — raté, silencieusement

curl -X POST "https://{region}.api.cognitive.microsoft.com/speechtotext/transcriptions:transcribe?api-version=2024-11-15" \
  -H "Ocp-Apim-Subscription-Key: {cle}" \
  -F "audio=@fichier.wav;type=audio/wav" \
  -F "definition=@definition.json;type=application/json"

Résultat : statut 200, une vraie transcription revenait... mais aucune information de locuteur, malgré la diarization demandée dans definition.json. Pas d'erreur, juste silencieusement ignoré — le genre de bug le plus dur à repérer : tout a l'air de marcher.

2

Retour à la documentation officielle

Deux choses en sont ressorties : le bon format JSON était déjà celui utilisé ({"diarization":{"enabled":true,"maxSpeakers":N}}) ; mais l'exemple officiel envoyait definition directement comme texte dans le formulaire, pas comme fichier joint.

3

Le vrai test, qui a marché

curl -X POST "https://{region}.api.cognitive.microsoft.com/speechtotext/transcriptions:transcribe?api-version=2025-10-15" \
  -H "Ocp-Apim-Subscription-Key: {cle}" \
  -F "audio=@fichier.wav;type=audio/wav" \
  -F 'definition={"locales":["fr-FR"],"diarization":{"maxSpeakers":4,"enabled":true}}'

Cette fois, la réponse contenait bien "speaker":1, "speaker":2... La différence tenait à un seul détail : envoyer definition comme valeur de champ (-F 'definition={...}') plutôt que comme fichier attaché (-F "definition=@fichier.json"). Azure traite ces deux formes différemment dans le multipart, sans le signaler par une erreur.

La leçon retenue pour la suite du projet — quand une API Azure "a l'air de marcher" (200, réponse plausible) mais qu'un comportement attendu manque, ne jamais supposer que c'est impossible : vérifier le format exact de la requête avant d'accuser l'API ou le service.

§ Le contrat de l'API, une fois découvert

Requête

Endpoint — POST .../speechtotext/transcriptions:transcribe?api-version=2025-10-15

En-tête — Ocp-Apim-Subscription-Key

Corps — multipart/form-data : audio (fichier joint), definition (texte brut, pas un fichier)

Réponse (extrait)

{
  "combinedPhrases": [{ "text": "texte complet du chunk" }],
  "phrases": [
    { "speaker": 1, "offsetMilliseconds": 80, "durationMilliseconds": 1800,
      "text": "Bonjour, je m'appelle Marie.", "confidence": 0.90 },
    { "speaker": 2, "...": "..." }
  ]
}

Le champ speaker est un entier (1, 2, 3...), présent uniquement quand la diarization est activée — c'est ce champ qui permet de savoir qui a dit quoi.

§ Les changements backend, fichier par fichier

Tous dans com.memoria.core.transcription.

SegmentLocuteur@Embeddable — nouveau 
@Embeddable
public class SegmentLocuteur {
    private int locuteur;
    private String texte;
    private long offsetMillisecondes;
    private long dureeMillisecondes;
}

Pas une entité à part entière avec son propre repository — juste un petit objet de valeur toujours chargé avec son Transcription parent. Un SegmentLocuteur = une prise de parole. Un chunk de 30s peut contenir plusieurs prises de parole de personnes différentes, d'où la liste.

TranscripteurPortun seul changement de type de retour 
public record ResultatTranscription(String texteComplet, List<SegmentLocuteur> segments) {}

public interface TranscripteurPort {
    ResultatTranscription transcrire(byte[] audio); // avant : String transcrire(byte[] audio)
}

Comme c'est une interface (un "port"), ce changement force à mettre à jour son unique implémentation et son unique appelant — exactement l'effet recherché : le compilateur indique où adapter le code.

TranscripteurAzureSpeechrécrit en grande partie

Construction manuelle du corps multipart. Le HttpClient de Java (java.net.http) n'a pas de méthode intégrée pour construire une requête multipart/form-data, contrairement à curl -F. Il faut fabriquer le corps à la main : une suite de sections séparées par une "frontière" (boundary, une chaîne UUID aléatoire à chaque appel), chacune avec ses propres en-têtes.

Simplification du format audio. L'ancienne API avait besoin qu'on lui dise explicitement le format audio envoyé, et le code inspectait les octets pour deviner WAV ou Ogg. La nouvelle API détecte le format toute seule — tout ce code de détection a été supprimé, plus simple qu'avant.

Extraction du résultat. combinedPhrases[0].text devient texteComplet, chaque élément de phrases[] devient un SegmentLocuteur.

Transcriptionentité, modifiée JPA 
@ElementCollection(fetch = FetchType.EAGER)
@CollectionTable(name = "transcription_segments_locuteur", joinColumns = @JoinColumn(name = "transcription_id"))
@OrderColumn(name = "position")
private List<SegmentLocuteur> segmentsLocuteur;

fetch = FetchType.EAGER — sans ça, Hibernate charge la liste "à la demande", et la lire après fermeture de la session de base de données (sérialisation JSON) plante. Déjà rencontré une fois avec Resume en Phase 1 — cette fois EAGER dès le départ. @OrderColumn garantit l'ordre chronologique des segments.

§ Frontend, et le lien avec le backend

Point essentiel — il n'y a pas de contrat partagé automatique entre le backend Java et le frontend TypeScript. SegmentLocuteurResponse (Java) et SegmentLocuteur (TypeScript) sont deux déclarations complètement séparées, à garder synchronisées à la main. Un renommage de champ côté Java sans le faire côté TypeScript n'est détecté par rien — juste une valeur undefined silencieuse.

types.ts

export interface SegmentLocuteur {
  locuteur: number
  texte: string
  offsetMillisecondes: number
  dureeMillisecondes: number
}

Noms de champs recopiés exactement depuis SegmentLocuteurResponse.java — Jackson sérialise en gardant le nom des champs tel quel.

SessionDetailPage.tsx

{segment.segmentsLocuteur.length > 0 ? (
  segment.segmentsLocuteur.map((l, i) => (
    <p key={i}><b>Intervenant {l.locuteur}</b> {l.texte}</p>
  ))
) : (
  <span>{segment.texte}</span>
)}

Si vide (ancien enregistrement d'avant ce changement), on retombe sur le texte complet — aucune session existante n'est cassée.

§ Comment on a vérifié que ça marchait vraiment

1

Test à 2 voix

Fichier audio généré avec deux voix de synthèse Windows différentes (Hortense en français, Zira en anglais), simulant "Marie" puis "Paul". Résultat : speaker:1 pour Marie, speaker:2 pour Paul — vérifié jusqu'à l'affichage réel dans le navigateur via Playwright.

2

Test à 3 voix

Même voix (Hortense) réutilisée pour deux "personnes" différentes (juste une vitesse de parole différente), plus une troisième voix distincte. Résultat : les deux premières fusionnées en un seul locuteur, la troisième ressortie séparément. Pas un bug — ça prouve que la diarization distingue par les caractéristiques acoustiques réelles (timbre, hauteur), pas par la vitesse d'élocution.

§ La limite connue, assumée, pas corrigée ici

—

Chaque chunk de 30s est transcrit indépendamment des autres

Consequence — si le chunk n°0 dit speaker:1 pour Marie, rien ne garantit que le chunk n°1 dira aussi speaker:1 pour Marie — Azure pourrait l'appeler speaker:2, chaque appel API étant traité comme une conversation à part.

Donc — la numérotation "Intervenant N" est fiable à l'intérieur d'un même chunk de 30s, mais pas garantie stable sur toute la session — encore moins d'une session à l'autre.

Reste a construire — la reconnaissance de voix récurrente (reconnaître "c'est la voix de Marie" indépendamment de l'ordre des chunks, et d'une session à l'autre) — explicitement prévue pour la Phase 3, pas encore construite.

§ Pour reprendre seul

  • Pour retester l'API Azure directement (sans passer par l'application), la commande curl de la section « Le contrat » fonctionne telle quelle — utile si Azure change encore le comportement de son API.
  • Pour ajuster le nombre maximum de locuteurs détectés : uniquement azure.speech.max-locuteurs dans application.properties, aucun code à toucher.
  • Chemin de bout en bout, même principe que partout ailleurs dans le projet : navigateur → SessionDetailPage.tsx → api.ts (obtenirTranscriptions) → TranscriptionController → TranscriptionService → base de données, puis retour en DTO.
