§ Le besoin

Point du roadmap Phase 5 : "suivi fin et tableaux de bord (entreprise)". Choisi comme suite du chantier engagements, sans dépendance externe non résolue — contrairement à la reconnaissance de voix récurrente, bloquée sur un choix de fournisseur (Azure Speaker Recognition retiré).

§ La règle qui cadre tout le reste

"Outil d'aide, pas de surveillance. Les rappels vont d'abord à la personne concernée. Le manager voit l'avancement global, pas le détail permanent des retards individuels. L'employé garde le contrôle de ses engagements." — master prompt

TableauDeBordEntrepriseResponse n'expose que des nombres agrégés — aucun champ ne permet de remonter à un Engagement ou un Utilisateur précis. Ce n'est pas une omission à combler : c'est la contrainte structurante de la brique. Note : aucun rôle "manager" ni structure d'équipe n'existe dans le modèle Entreprise actuel — le tableau agrège donc sur tous les engagements du système.

§ Les décisions de conception

  • Agrégation en mémoire — findAll() + streams Java plutôt que du JPQL GROUP BY. Simplicité assumée, volume actuel ne justifie pas l'optimisation.
  • Taux de complétion excluant les rejetés — termines / (total - rejetes). Un engagement rejeté n'a jamais eu vocation à être terminé ; l'inclure fausserait le taux à la baisse.
  • Couleurs reprises de l'existant, pas inventées — skill dataviz invoqué avant d'écrire le graphique. Les quatre statuts reprennent les teintes déjà utilisées sur les badges d'EngagementsPage (ambre/bleu/vert/gris), en -500/-400 pour rester dans la bande de luminosité OKLCH validée. Sous le seuil de contraste 3:1 pour certaines teintes (attendu pour des couleurs de statut) — mitigé par une légende texte toujours visible.

§ Limites connues, assumées

  • Pas de scope par équipe/manager — aucune notion de ce type n'existe dans le modèle Entreprise actuel.
  • Pas de tendance temporelle — aucun historique des transitions de statut n'est conservé ; ajouter cela demanderait une nouvelle table d'historique.
  • Agrégation en mémoire — choix de simplicité, pas optimisé pour un grand volume.
  • Aucun filtre (période, type de session) — une seule vue globale dans cette première brique.

§ Pour reprendre seul

  • Pour une tendance temporelle : journaliser d'abord les transitions de statut (nouvelle table d'historique), puis agréger par période.
  • Pour un scope par équipe : dépend d'abord de l'introduction d'une notion d'équipe/projet dans le modèle Entreprise — ne pas anticiper la forme avant que le besoin soit confirmé.
  • Chemin de bout en bout : TableauDeBordPage.tsx → obtenirTableauDeBordEntreprise (api.ts) → TableauDeBordEntrepriseController → TableauDeBordEntrepriseService → EngagementRepository.findAll().
