§ Le besoin

Le master prompt qualifie sa section Gouvernance des données de "condition d'entrée dans les secteurs régulés, pas un raffinement tardif". Recherche confirmée dans le code avant de concevoir cette brique : zéro ligne existait pour ce chapitre après 12 phases.

§ Les décisions de conception

  • Session personnelle → purge, session partagée → anonymisation — impossible de supprimer en bloc une session partagée pour l'effacement d'un seul participant. Réutilise l'état déjà supporté createurId = null des sessions historiques.
  • Deux précédents réutilisés tels quels — EmpreinteVocaleService.revoquer (DB autoritaire, nettoyage externe best-effort) et CouloirService.transfererPropriete/supprimerCouloir (déjà résolu : que devient un contenu partagé quand son propriétaire disparaît).
  • Le piège de l'auto-invocation Spring — @Transactional est ignoré sur un appel interne au même bean. Deux méthodes publiques distinctes, orchestrées par le contrôleur.
  • "Instance = tenant" pour la rétention — même raisonnement que le budget Azure en phase-11 : une durée globale, désactivée par défaut, aucun concept de tenant à construire.

§ Limites connues, assumées

  • Chiffrement au repos/transit — ni implémenté, ni encore documenté dans docs/deploiement.md (vérifié explicitement) — vrai trou infrastructure.
  • Consentement des participants — différé, brique de capture séparée.
  • Aucun rôle admin — effacement/export strictement self-service.
  • Matiere.createurId non anonymisé (nullable=false, faible sensibilité).
  • FilMemoire.resumeCumulatif non retouché après retrait d'une session — régénérer demanderait une vraie opération IA.

§ Pour reprendre seul

  • Toute nouvelle donnée personnelle future : l'ajouter aux deux endroits symétriques effacerCompte et exporterDonnees.
  • Prochaine direction possible : chiffrement au repos/transit (brique infrastructure), consentement à l'enregistrement, rôle admin si besoin confirmé.
