Déploiement mono-instance industrialisé (Docker + Terraform)

Premier incrément de ce que le master prompt pose comme non-négociable : "Docker + Terraform ne sont pas décoratifs, ils rendent le modèle économique possible." Une VM Azure unique fait tourner la stack complète (backend, frontend, speaker-service, Postgres) via Docker Compose — pas d'AKS pour ce premier incrément.

§ Le besoin

Le master prompt : "une instance dédiée par client... déploiement mono-instance industrialisé (rapide, automatisé via Docker + Terraform), pas le cloisonnement interne", et : "Docker + Terraform + CI/CD ne sont pas décoratifs : ils rendent le modèle économique (vente en instance dédiée par client) possible." Sans ça, le modèle "une instance par client" reste un bricolage manuel, pas industrialisable. État avant cette brique : speaker-service/Dockerfile seul existait, docker-compose.yml ne contenait que Postgres, aucun Terraform, la CI ne testait que le code sans jamais construire d'image.

§ Les décisions de conception

  • VM Azure unique + Docker Compose, pas AKS — AKS est nommé dans le master prompt mais correspond à la Phase 4 "Plateforme/passage à l'échelle", prématuré sans client réel. Mêmes conteneurs réutilisables tels quels si AKS est adopté plus tard.
  • Terraform construit et validé, jamais appliqué — aucun identifiant Azure de production disponible ; créer de vraies ressources facturées exige une confirmation explicite.
  • Aucun secret applicatif dans Terraform — le state stocke tout en clair ; JWT/clés Azure AI vivent dans un .env copié séparément sur la VM.
  • speaker-service jamais exposé au-delà du réseau Docker — son README documente l'absence d'authentification avec le backend ; mitigation immédiate sans construire l'authentification manquante.
  • Ajout de spring-boot-starter-actuator — le projet n'avait aucun endpoint de santé, indispensable pour que depends_on: condition: service_healthy ait un sens.
  • Build multi-stage Maven-in-Docker plutôt que jar pré-construit — garde docker build autonome et reproductible sur n'importe quelle machine.

§ Les fichiers, un par un

1

backend/Dockerfile — multi-stage

FROM maven:3.9-eclipse-temurin-21 AS build
...
FROM eclipse-temurin:21-jre-alpine
RUN apk add --no-cache curl
HEALTHCHECK ... CMD curl -f http://localhost:8080/actuator/health || exit 1
2

SecurityConfig.java — sonde de sante ouverte

.requestMatchers("/actuator/health").permitAll()

Note — sans ca, le mur de securite existant (anyRequest().authenticated()) aurait bloque le HEALTHCHECK Docker avec un 401.

3

frontend/Dockerfile + nginx.conf

location /api/ { proxy_pass http://backend:8080/api/; }
location / { try_files $uri $uri/ /index.html; }
4

docker-compose.yml — etendu, postgres inchange

Ajoute backend, speaker-service (sans port publie), frontend (seul service publie, port 80). Volumes persistants pour audio/documents/profils vocaux.

5

infra/terraform/ — VM Azure unique

versions.tf, main.tf (resource group, vnet/subnet, NSG restrictif, VM Linux Standard_B2s + cloud-init), variables.tf (domaine par defaut memoria.episen.fr), outputs.tf, terraform.tfvars.example.

§ Comment on a vérifié en conditions réelles

Deux bugs préexistants ont bloqué la première tentative de docker compose build — corrigés en route, nécessaires pour une vérification réelle :

1

speaker-service/requirements.txt — numpy incompatible avec Python 3.11

numpy==2.5.1 exige Python ≥3.12, incompatible avec python:3.11-slim du Dockerfile existant (non modifié). Corrigé en numpy==2.2.6.

2

frontend/api.ts — erasableSyntaxOnly, en echec silencieux depuis le debut de la session

Propriete de constructeur raccourcie interdite par erasableSyntaxOnly: true. Ce bug faisait deja echouer tsc -b --noEmit depuis le debut de cette session, masque a chaque fois par le cache incremental local — un build Docker, toujours propre, l'a revele pour de vrai. Corrige.

§ Limites connues, assumées

  • Pas d'AKS — VM unique + Docker Compose seulement.
  • Pas de Kafka, Entra ID, Key Vault, ni Azure Blob Storage — hors perimetre explicite.
  • Stockage sur disque local (volumes Docker), pas Azure Blob.
  • Pas de push d'image ni de deploiement automatique — la CI construit comme garde-fou seulement.
  • terraform apply jamais execute — aucune VM Azure reelle n'existe a ce jour.
  • Deploiement du .env reel sur la VM entierement manuel (scp).

§ Pour reprendre seul

  • Local : docker compose up --build → frontend (nginx, :80) → proxy /api/* → backend (:8080 interne) → postgres/speaker-service (interne uniquement).
  • Cloud (code pret, jamais applique) : cd infra/terraform && terraform apply (avec de vrais identifiants) → VM provisionnee avec Docker → deployer manuellement le depot + .env reel.
  • Prochaine direction retenue : observabilite minimale (Prometheus + Grafana + OpenTelemetry), explicitement liee a Docker/Terraform dans le master prompt.
