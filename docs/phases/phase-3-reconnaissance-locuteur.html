§ Le besoin

Point du roadmap Phase 3, jamais construit. Déclencheur concret : Engagement.responsable n'est qu'un label de diarization ("Intervenant 2"), jamais lié à un vrai compte Utilisateur — limite documentée deux fois lors du chantier engagements de cette session. Choisi comme direction suivante après sa clôture.

Enrôlement : flux dédié, ~20s de voix, consentement explicite (biométrique RGPD, opt-in, révocable). Portée : identification affichée seulement — Engagement.responsable et le ciblage des rappels ne changent pas, chantier séparé.

§ Les décisions de conception

  • Groupement par (chunk, locuteur), jamais par locuteur seul — reflète fidèlement la contrainte du §2. Une personne parlant dans 10 chunks reçoit jusqu'à 10 appels indépendants ; pas de recollement inter-chunks dans cette brique.
  • Identification événementielle et par lot — IdentificationLocuteurService écoute SessionTermineeEvent (comme ResumeService/FilMemoireService), pas ChunkAudioEnregistreEvent : un seul passage par session, discipline de coûts.
  • Jamais marquer une identification "faite" si elle n'a pas eu lieu — même classe de garde que pour les rappels d'engagements.
  • Idempotence via l'état du segment — pas de table de suivi séparée ; SegmentLocuteur reste immuable (avecIdentification(...) reconstruit une copie).
  • Un profil vocal par utilisateur — le ré-enrôlement supprime l'ancien profil externe (best-effort) avant d'en créer un nouveau.

Même principe que le faux serveur SMTP utilisé plus tôt dans le projet : IdentificateurLocuteurFactice (profil Spring verification-locuteur, jamais actif par défaut), différencie déterministiquement par la longueur en octets de l'échantillon — signal dérivé de l'audio réel, pas un mock aveugle.

§ Découverte en cours de vérification : Azure Speaker Recognition est retiré

⚠

En préparant un test contre le vrai Azure (les credentials AZURE_SPEECH_KEY/AZURE_SPEECH_REGION se sont révélées configurées dans l'environnement), une recherche a confirmé que Azure Speaker Recognition a été retiré par Microsoft le 30 septembre 2025 — pas une question d'accès restreint (Limited Access, le risque anticipé avant de coder), un service qui n'existe plus du tout. Aucun remplacement direct proposé par Microsoft dans Azure. Alternatives citées : modèles auto-hébergés (pyannote, SpeechBrain, WeSpeaker) ou d'autres clouds (AWS Connect Voice ID, Google SpeakerID).

IdentificateurLocuteurAzureSpeech est donc non fonctionnel en l'état — documenté clairement dans le commentaire de classe, gardé comme référence de forme en attendant un choix de fournisseur. Le port IdentificateurLocuteurPort isole cette décision : remplacer cette seule classe suffira.

§ Limites connues, assumées

  • Aucun fournisseur d'identification réellement fonctionnel — voir §7. Brique complète et vérifiée dans tout ce qui l'entoure, mais inerte en production tant qu'un remplaçant n'est pas choisi.
  • Pas de recollement inter-chunks — assumé, plusieurs identifications indépendantes par session possibles.
  • Pas de ciblage de Engagement.responsable/rappels — scope limité à l'affichage.
  • Pas de ré-identification rétroactive des sessions déjà enregistrées.
  • Pas d'effacement rétroactif des identifications déjà écrites à la révocation.
  • Seuil de confiance (0.70) non calibré — placeholder, à revoir avec un vrai fournisseur.

§ Pour reprendre seul

  • Pour remplacer le fournisseur : implémenter IdentificateurLocuteurPort avec le nouveau choix, retirer/supprimer l'ancienne classe Azure — rien d'autre à toucher.
  • Chemin de bout en bout : ParametresCompteePage.tsx → EmpreinteVocaleController/Service → IdentificateurLocuteurPort.enroller → ... → SessionTermineeEvent → IdentificationLocuteurService → ExtracteurAudioLocuteur → IdentificateurLocuteurPort.identifier → Transcription.identifierLocuteur → TranscriptionService.obtenirTranscriptionsAvecIdentification → SessionDetailPage.tsx.
  • Vérification factice : SPRING_PROFILES_ACTIVE=verification-locuteur.
