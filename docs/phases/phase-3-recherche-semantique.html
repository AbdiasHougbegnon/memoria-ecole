§ Le besoin

memoria-master-prompt.md demande de retrouver « le passage exact, avec son timestamp », sur tout l'historique des sessions — pas juste dans une session à la fois. Ce n'est pas un Ctrl+F : taper « c'est quand qu'on a parlé du budget ? » doit retrouver le passage même si personne n'a jamais dit le mot « budget », parce qu'on cherche une signification, pas une chaîne de caractères.

C'est la première brique de la Phase 3, et la première du projet à utiliser une base de données vectorielle.

§ Concepts clés, avant le code

Embedding (vecteur)

Une liste de 1536 nombres qui représente le sens d'un texte. Deux phrases qui veulent dire la même chose, même écrites très différemment, ont des listes de nombres mathématiquement proches. Un modèle d'IA (text-embedding-ada-002) fait cette transformation.

Recherche vectorielle (KNN)

Vectoriser la question, puis demander « quels vecteurs stockés sont les plus proches de celui-ci ? ». Azure AI Search utilise HNSW pour éviter de comparer à tous les vecteurs un par un. Piège : ça renvoie toujours les k plus proches, même si rien n'est pertinent — jamais de vrai « aucun résultat ».

Ports & adaptateurs

Une interface Java qui décrit le besoin (RecherchePort, GenerateurEmbeddingPort), une classe qui sait parler à Azure (RechercheAzureAiSearch, GenerateurEmbeddingAzureOpenAI). Deux ports séparés parce que ce sont deux ressources Azure indépendantes, remplaçables chacune de leur côté.

§ Décisions de conception

Quelle granularité indexer ?

Session entière, chunk de 30s, ou segment de locuteur ? Choisi : le segment — le seul niveau qui a déjà un offsetMillisecondes précis (diarization, Phase 2), exigé par CLAUDE.md : « traçable jusqu'au passage exact ». Coût maîtrisé en envoyant tous les segments d'une session en un seul appel d'embeddings.

Quand déclencher l'indexation ?

À la fin de session, pas chunk par chunk — le besoin est une recherche historique, pas temps réel. Réutilise exactement le mécanisme d'événements déjà en place pour les résumés.

pgvector ou Azure AI Search ?

pgvector était recommandé par défaut (gratuit, cohérent avec l'approche monolithe du projet). L'utilisateur a choisi Azure AI Search explicitement — service managé dédié, reranking et recherche hybride disponibles. Ce choix a entraîné tout le provisionnement de la section suivante.

§ Provisionner les ressources Azure — le vrai parcours

Deux choses à créer : un déploiement de modèle d'embeddings sur memoria-openai, et — déjà là — la ressource Azure AI Search elle-même. Rien ne s'est passé du premier coup.

1

az login a résisté

az login classique n'ouvrait jamais de navigateur. --use-device-code obtenait bien un token mais az account show répondait toujours « Please run az login » (souscriptions vides). Contournement : tout faire depuis Azure Cloud Shell (déjà authentifié via le portail) plutôt que perdre du temps en local.

2

Trouver la ressource et les modèles disponibles

az cognitiveservices account list --query "[].{name:name, resourceGroup:resourceGroup, kind:kind}" -o table
az cognitiveservices account list-models --name memoria-openai --resource-group memoria-rg -o table

memoria-rg / memoria-openai. Modèles candidats : text-embedding-3-small (recommandé au départ), text-embedding-ada-002, text-embedding-3-large.

3

SKU incompatible, puis quota à zéro

text-embedding-3-small + SKU Standard → SKU non supporté dans francecentral. Avec GlobalStandard → quota disponible = 0, sur ce compte Azure for Students. Vérifié précisément avec :

az cognitiveservices usage list --location francecentral --query "[?contains(name.value,'embedding')]" -o json

OpenAI.Standard.text-embedding-ada-002 avait 240K TPM disponibles. Décision (validée avec l'utilisateur) : basculer sur ada-002.

4

Le déploiement qui a marché — puis sa capacité augmentée

az cognitiveservices account deployment create --name memoria-openai --resource-group memoria-rg \
  --deployment-name text-embedding-ada-002 --model-name text-embedding-ada-002 --model-version "2" \
  --model-format OpenAI --sku-name "Standard" --sku-capacity 10

Capacité initiale à 1 (1000 tokens/min) — insuffisante pour une vraie session (section Erreurs). Portée à 10. Nom de déploiement utilisé tel quel dans AZURE_OPENAI_EMBEDDING_DEPLOYMENT.

§ Les fichiers backend, un par un

Tous dans com.memoria.core.recherche — remarque core, pas entreprise/ecole : la recherche est une fonctionnalité du moteur partagé.

RechercheServicele chef d'orchestre

indexerSiPossible(sessionId) — 4 étapes : (1) garde d'idempotence (un IndexRecherche existant fait sortir tout de suite), (2) filtre les transcriptions REUSSIE, (3) aplatit tous les SegmentLocuteur en List<SegmentARecherche> en retirant les textes vides, (4) un seul appel genererEmbeddings puis indexerSegments — toute exception attrapée marque ECHEC plutôt que de planter.

@Async @EventListener
public void surSessionTerminee(SessionTermineeEvent e) { indexerSiPossible(e.sessionId()); }
@Async @EventListener
public void surToutesTranscriptionsTerminees(ToutesTranscriptionsTermineesEvent e) { indexerSiPossible(e.sessionId()); }

Pourquoi deux déclencheurs identiques ? Fin de session et dernière transcription arrivent dans un ordre imprévisible (course connue, déjà rencontrée pour les résumés). Les deux appellent la même logique idempotente — peu importe l'ordre, jamais de double indexation.

rechercher(requete, limite) vectorise la question puis délègue au port, en transmettant aussi le texte brut (recherche hybride). reindexerHistorique() — voir section dédiée plus bas.

RecherchePort → RechercheAzureAiSearchl'adaptateur Azure AI Search

assurerIndexExiste() (@PostConstruct, exécutée au démarrage) : PUT idempotent qui crée ou met à jour l'index — l'application s'auto-provisionne son propre schéma, aucune étape manuelle.

indexerSegments(...) : construit un document par segment avec "@search.action":"mergeOrUpload" — id déterministe {sessionId}_{numeroSequence}_{offsetMillisecondes}, donc rappeler deux fois ne duplique jamais rien.

rechercher(texteRequete, vecteurRequete, limite) : envoie vectorQueries et search dans la même requête — recherche hybride, voir Erreurs.

GenerateurEmbeddingPort → GenerateurEmbeddingAzureOpenAItexte → vecteur

genererEmbeddings(List<String>) — toujours une liste, jamais un texte à la fois (un seul appel HTTP par session). Azure ne garantit pas l'ordre de retour : chaque élément a un champ index, trié explicitement avant de renvoyer les vecteurs, pour que vecteurs.get(i) corresponde toujours à textes.get(i).

IndexRecherchel'entité de garde entité

Une ligne par session (sessionId unique), avec juste nombreSegments et statut (REUSSI/ECHEC). Ne contient aucun vecteur, aucun texte — le vrai contenu vit entièrement dans Azure AI Search. Cette table n'est qu'un marqueur pour la garde d'idempotence.

RechercheController/api/v1/recherche

GET ?q=...&limite=10 — global, pas scopé à une session, reflet direct du besoin « tout l'historique ». POST /reindexation renvoie 202 Accepted (travail en arrière-plan, pas de suivi de progression).

§ Le frontend, et les bases de React utilisées ici

RecherchePage.tsx — si React est encore nouveau, voici chaque notion utilisée, à partir du code réel.

useState — la mémoire d'un composant

const [requete, setRequete] = useState('')

Appeler setRequete(...) ne modifie pas juste une variable : ça dit à React « réaffiche ce composant ». 5 cases mémoire dans cette page (requete, resultats, chargement, aRecherche, reindexationLancee).

Champ « contrôlé »

<input value={requete} onChange={e => setRequete(e.target.value)} />

La valeur affichée vient entièrement de l'état React, jamais du navigateur seul — chaque frappe met à jour l'état, qui réaffiche le champ.

Soumission async, avec finally

e.preventDefault()
setChargement(true)
try { setResultats(await rechercher(requete)) }
finally { setChargement(false) }

finally garantit que le bouton se réactive même si la recherche échoue — sinon il resterait bloqué indéfiniment.

Affichage conditionnel & listes

{aRecherche && !chargement && resultats.length === 0 && (...)}
{resultats.map((r, i) => <li key={i}>...</li>)}

condition && élément n'affiche rien si condition est fausse. .map() transforme un tableau en JSX, jamais de boucle for dans le rendu.

Le lien de « drill-down » (<Link to={\`/sessions/${'{'}resultat.sessionId{'}'}\`}>) change de page sans recharger l'appli — c'est la traçabilité CLAUDE.md : redescendre du résultat de recherche vers la session complète.

§ Réindexer l'historique

Fonctionnalité apparue en testant, pas prévue à la conception : toutes les sessions créées avant cette brique n'ont jamais déclenché surSessionTerminee — jamais indexées sans rattrapage.

reindexerHistorique() réutilise exactement indexerSiPossible — aucune nouvelle logique, juste une nouvelle façon de la déclencher : parcourir toutes les sessions TERMINEE. La garde d'idempotence filtre les déjà-traitées toute seule.

§ Erreurs rencontrées, dans l'ordre

01

Conflit de schéma d'index

Symptôme — statut 400 — "Existing field 'id' cannot be changed" au démarrage.

Cause — un index de test créé à la main (curl) avec un schéma légèrement différent du code Java final. Azure autorise d'ajouter des champs à un index existant, jamais de changer leurs propriétés.

Correctif — DELETE /indexes/memoria-segments, laissé recréer proprement au redémarrage.

02

Limite de débit dépassée (RateLimitReached)

Symptôme — réindexation d'une vraie session (30 segments, ~1239 tokens estimés) : RateLimitReached.

Cause — capacité de déploiement au minimum (1000 tokens/min) — juste assez pour un test unitaire, pas pour une vraie session.

Correctif — capacité portée à 10 (10K tokens/min). Une vraie réunion de 30 min dépasse largement 1000 tokens : ne jamais laisser une capacité minimale « juste pour tester ».

03

Précision médiocre du vecteur seul

Symptôme — utilisateur : « c'est pas beaucoup précis ». Question pertinente → score 0.887 ; question hors-sujet → 0.831. Écart de 0.05, trop faible.

Cause — propriété connue de ada-002 : scores cosinus resserrés dans une bande étroite (souvent 0.8-0.9), peu importe la pertinence réelle.

Correctif — recherche hybride (vecteur + BM25, fusionnés par Azure via RRF). Après correctif : 3 résultats pertinents groupés (0.033/0.031/0.031) puis chute nette (0.025), contre un seul résultat marginal (0.029) puis chute immédiate (0.017) pour le bruit. Coût : zéro, aucune réindexation nécessaire.

§ Comment on a vérifié que ça marchait vraiment

1

API brute au curl, avant tout code Java

Index de test, vrai vecteur, question reformulée différemment du texte source → bon document en premier (score 0.855).

2

End-to-end avec données insérées directement en base

Session créée via l'API, transcription/segments insérés en SQL, puis terminer déclenche l'indexation réelle (vrais appels Azure). Question reformulée → bon passage en premier.

3

Interface avec Playwright

Recherche, capture d'écran, clic réel sur le lien de résultat, vérification de l'URL obtenue, aucune erreur console.

4

Vraie session existante du projet

« Comment le couple a-t-il trouvé sa fortune ? » retrouve le passage sur le trésor — alors que le mot « fortune » n'apparaît nulle part (la transcription dit « trillionnaires »).

5

Réindexation en masse sur toute la base réelle

Suivie en interrogeant directement PostgreSQL jusqu'à stabilisation — a révélé la limite des 27 sessions sans segments.

§ Limites connues, assumées

  • KNN renvoie toujours des résultats, même hors-sujet — amélioré par l'hybride, pas résolu à la racine. Reranking sémantique payant ou text-embedding-3-large (quota dispo, mais réindexation complète nécessaire) seraient les prochaines étapes.
  • 27 sessions historiques non cherchables (avant la diarization) — assumé, ne se reproduira plus.
  • Pas de suivi de progression de la réindexation en masse — 202 immédiat, sans indicateur d'avancement dans l'interface.
  • Capacité Azure OpenAI (10K tokens/min) pragmatique, pas dimensionnée pour du multi-utilisateur massif — à revoir en Phase 4 (multi-tenant).

§ Pour reprendre seul

  • Recréer les ressources Azure : suivre la section « Provisionner » dans l'ordre — utiliser le Cloud Shell, pas az login en local.
  • Modifier le schéma de l'index : supprimer l'index existant (DELETE /indexes/memoria-segments) avant de relancer, sinon Azure refuse la mise à jour — puis relancer POST /api/v1/recherche/reindexation.
  • Changer de modèle d'embeddings : nouveau déploiement Azure → AZURE_OPENAI_EMBEDDING_DEPLOYMENT → DIMENSIONS_VECTEUR dans RechercheAzureAiSearch.java si la dimension change → supprimer/recréer l'index → réindexer.
  • Chemin de bout en bout : navigateur → RecherchePage.tsx → api.ts → RechercheController → RechercheService → les deux ports → Azure OpenAI + Azure AI Search, puis retour en DTO.
