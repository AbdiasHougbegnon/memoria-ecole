Séparation École/Entreprise en deux modules

École et Entreprise étaient mélangés dans les mêmes pages (une section "Entreprise" et une section "Ecole" côte à côte sur le détail de session, une nav unique). Chaque compte appartient désormais à un module choisi à l'inscription, avec un écran de sélection dédié, une identité visuelle propre à chaque module, et des routes API restreintes côté serveur — le tout sans toucher au moteur commun.

§ Le besoin

École et Entreprise étaient mélangés dans les mêmes pages frontend : le détail de session affichait côte à côte "Compte rendu complet (Entreprise)" et "Résumé de cours (Ecole)", la nav mélangeait liens génériques et liens Entreprise sans distinction visuelle, et la connexion ne portait aucune notion de produit. Demande explicite : deux modules réellement séparés, regroupés par le moteur commun, connexion module-aware. Kafka et les microservices séparés restent hors périmètre — reportés à un signal réel (deuxième développeur ou premier déploiement client).

Trois décisions tranchées avant conception :

  • Module persisté sur le compte — champ sur Utilisateur, choisi à l'inscription.
  • Écran de sélection dédié avant le login — pas un simple toggle sur le formulaire.
  • Identité visuelle par module pour les pages du moteur partagé (nav/couleurs différentes, même fonctionnalité).

§ Les décisions de conception

  • Suivre le chemin déjà anticipé pour un futur role — phase-5-securite-auth.md décrivait déjà : champ sur Utilisateur, autorité dans JwtAuthenticationFilter, hasRole(...) dans SecurityConfig. Appliqué tel quel avec module.
  • ModuleMemoria dans core.auth, jamais dans un package produit — même principe que Couloir/MembreCouloir : le moteur ne connaît ni Ecole ni Entreprise.
  • Module dans le JWT, pas relu en base — JwtAuthenticationFilter reste stateless. Limite assumée : un changement de module ne serait pris en compte qu'à la réémission du token (24h) — sans conséquence, aucun endpoint ne permet ce changement.
  • Restriction dans SecurityConfig, pas dans les services — un contrôle de module est une autorisation, pas une règle métier ; hasAuthority("MODULE_ENTREPRISE") centralise la logique.
  • Mauvais écran de login → redirection silencieuse — le module vient toujours du serveur, jamais de l'URL cliquée ; refuser la connexion n'apporterait aucun bénéfice de sécurité.
  • Split de SessionDetailPage en sous-composants — le fetch devait de toute façon devenir conditionnel au module (sinon 403 pour l'autre module), donc extraction complète plutôt qu'un simple if de rendu.

2

@Enumerated(EnumType.STRING)
@Column(nullable = false, length = 20)

Note — ancien constructeur à 2 arguments retiré, tous les appelants (code + tests) mis à jour.

3

JwtService — claim module + validerEtExtraire

.claim("module", utilisateur.getModule().name())
// ...
public record UtilisateurAuthentifie(UUID utilisateurId, ModuleMemoria module) {}
public Optional<UtilisateurAuthentifie> validerEtExtraire(String token) { ... }
4

SecurityConfig — restriction des routes par module

.requestMatchers("/api/v1/engagements/**").hasAuthority("MODULE_ENTREPRISE")
.requestMatchers("/api/v1/entreprise/**").hasAuthority("MODULE_ENTREPRISE")
.requestMatchers("/api/v1/sessions/*/compte-rendu").hasAuthority("MODULE_ENTREPRISE")
.requestMatchers("/api/v1/sessions/*/resume-cours").hasAuthority("MODULE_ECOLE")
// tout le reste (sessions, couloirs, recherche, transcriptions...) : anyRequest().authenticated()

§ Les tests

cd backend && mvn test — 164/164 tests passent (162 précédents + 2 nouveaux : stockage du module à l'inscription, round-trip du module dans le JWT). Les tests des autres services (Session, Transcription, CompteRendu, Engagement, Rappel) ont simplement leurs constructeurs Utilisateur mis à jour, sans nouvelle assertion. cd frontend && npx tsc -b --noEmit — zéro nouvelle erreur (une erreur pré-existante sans rapport sur api.ts:7, confirmée antérieure via git stash). npm run lint — clean.

Pas de nouveau test @WebMvcTest pour SecurityConfig — convention déjà explicite dans ResumeControllerTest : règles Spring Security couvertes par les tests dédiés à JwtService/AuthService et par la vérification manuelle end-to-end.

§ Limites connues, assumées

  • Pas de changement de module après inscription — aucun endpoint ne le permet ; cohérent avec le modèle de déploiement cible (une instance dédiée par client).
  • Module du JWT jamais re-vérifié en base pendant 24h — sans conséquence tant qu'aucun changement de module n'est possible.
  • Migration manuelle, pas de Flyway/Liquibase — acceptable en Phase 1, à revoir si un vrai déploiement client l'exige.
  • Kafka et microservices séparés hors périmètre — reporté à un signal réel, choix délibéré, pas un oubli.

§ Pour reprendre seul

  • Chemin de bout en bout : ChoixModulePage → LoginPage (lit ?module=) → POST /inscription ou /connexion → AuthResponse.module → enregistrerSession → RouteProtegee + Layout → chaque requête porte le JWT avec la claim module → SecurityConfig autorise ou bloque.
  • Prochaine direction retenue : Docker + Terraform pour un déploiement mono-instance industrialisé — ce que le master prompt pose explicitement comme ce qui compte techniquement pour un vrai client.
