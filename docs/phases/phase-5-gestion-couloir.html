Gestion du couloir par son propriétaire

Renommer, supprimer, retirer un membre — trois actions jusque-là impossibles alors que Couloir.proprietaireId existait déjà. Cette brique les construit, et documente un bug réel de transaction trouvé pendant la vérification manuelle avec de vrais comptes.

§ Le besoin

Depuis la première brique des couloirs de classe (tag phase-5-couloirs-classe), le champ Couloir.proprietaireId existe mais n'est utilisé pour aucune vérification de permission — limite explicitement notée à l'époque. Concrètement : impossible de renommer un couloir mal nommé, impossible de le supprimer, impossible de retirer un membre qui n'a rien à y faire.

Choisi comme prochaine étape avec l'utilisateur, plutôt que les rappels/notifications côté Entreprise — un chantier plus gros, qui suppose de choisir une infrastructure de notification en amont.

§ Les décisions de conception

  • Périmètre : trois actions, rien de plus — renommer, supprimer, retirer un membre, plus un endpoint de lecture des membres nécessaire à l'UI. Hors périmètre : transfert de propriété, "quitter le couloir soi-même" (action différente, pour un membre non propriétaire — pas demandée).
  • Mutation via méthode métier nommée — Couloir.renommer(String) plutôt qu'un setNom() générique, cohérent avec Session.terminer() et Engagement.confirmer() déjà dans le projet.
  • Retrait du propriétaire lui-même : 409, pas 403 — la requête est autorisée (il agit dans son propre couloir), mais l'état demandé (couloir sans propriétaire) est invalide. Distinction assumée d'avec PasProprietaireDuCouloirException (403, question d'autorisation).
  • Suppression d'un couloir : les sessions rattachées ne bougent pas — session.couloirId est une référence brute sans contrainte FK (comme partout dans le projet). Les sessions redeviennent visibles à leur seul créateur ; pas de cascade qui effacerait l'historique d'enregistrement de quelqu'un.

La découverte technique de cette brique : le bug @Transactional

@Transactional
public void supprimerCouloir(UUID couloirId, UUID utilisateurId) {
    Couloir couloir = obtenirCouloir(couloirId);
    verifierProprietaire(couloir, utilisateurId);
    membreCouloirRepository.deleteByCouloirId(couloirId);
    couloirRepository.deleteById(couloirId);
}

@Transactional
public void retirerMembre(UUID couloirId, UUID membreARetirerId, UUID utilisateurId) {
    Couloir couloir = obtenirCouloir(couloirId);
    verifierProprietaire(couloir, utilisateurId);
    if (membreARetirerId.equals(couloir.getProprietaireId())) {
        throw new ProprietaireNePeutPasSeRetirerException(couloirId);
    }
    membreCouloirRepository.deleteByCouloirIdAndUtilisateurId(couloirId, membreARetirerId);
}

Pourquoi c'est nouveau — premier usage de @Transactional dans tout le projet (confirmé par grep avant d'écrire la ligne). Les méthodes de suppression dérivées de Spring Data (définies dans l'interface repository, pas héritées de JpaRepository) ne sont pas transactionnelles par défaut — contrairement aux méthodes héritées (save(), deleteById()) qui obtiennent leur propre transaction par appel via SimpleJpaRepository. Détail complet du bug trouvé en conditions réelles : §6.

GestionnaireExceptionsApi — deux entrées ajoutées : PasProprietaireDuCouloirException → 403, ProprietaireNePeutPasSeRetirerException → 409.

§ Le frontend

  • auth.ts — enregistrerSession stocke désormais aussi utilisateurId (nouvelle clé localStorage), nouvelle fonction obtenirUtilisateurIdConnecte(). Nécessaire pour comparer l'utilisateur courant à couloir.proprietaireId sans appel réseau supplémentaire.
  • CouloirDetailPage.tsx — tout le bloc de gestion (renommage, liste des membres avec bouton "Retirer", suppression) n'est rendu que si couloir.proprietaireId === obtenirUtilisateurIdConnecte(). Le bouton "Retirer" est lui-même absent en face du propriétaire — pas de tentative d'auto-retrait possible depuis l'UI, en plus de la garde 409 côté serveur.

§ Limites connues, assumées

  • Pas de transfert de propriété — un couloir reste éternellement propriété de son créateur. Hors périmètre, pas demandé.
  • Pas de "quitter le couloir soi-même" pour un membre non propriétaire — seul le propriétaire peut retirer quelqu'un aujourd'hui.
  • Décompte de membres affiché non rafraîchi après un retrait — CouloirDetailPage.tsx calcule "X membre(s)" une seule fois depuis l'objet initial. Défaut d'affichage pur, sans conséquence fonctionnelle ; laissé tel quel.
  • Le même patron @Transactional manquant pourrait exister ailleurs — audité, écarté. Recherche exhaustive dans les 13 interfaces repository du projet (deleteBy, updateBy, @Modifying, @Query) : MembreCouloirRepository.deleteByCouloirId/deleteByCouloirIdAndUtilisateurId étaient les seules méthodes de mutation dérivées de tout le projet, déjà corrigées. Toutes les autres méthodes déclarées ailleurs sont en lecture seule ; les deux seules @Query du projet sont des SELECT, aucune @Modifying. Pattern isolé aux couloirs — pas de dette cachée ailleurs sur ce point précis.

§ Pour reprendre seul

  • Le bug @Transactional a été audité sur tout le reste du projet (voir §7) : rien d'autre à corriger. Si une future méthode de repository définie dans l'interface (pas héritée de JpaRepository) modifie des données (deleteBy..., updateBy..., @Modifying), reproduire le même réflexe : confirmer qu'elle est appelée depuis une méthode de service annotée @Transactional.
  • Pour le transfert de propriété (non construit) : CouloirService.transfererPropriete(couloirId, nouveauProprietaireId, utilisateurId) avec la même garde verifierProprietaire, plus une vérification que le nouveau propriétaire est déjà membre.
  • Chemin de bout en bout : CouloirDetailPage.tsx (rendu conditionnel) → api.ts (renommerCouloir/supprimerCouloir/listerMembresCouloir/retirerMembreCouloir) → CouloirController → CouloirService (verifierProprietaire à chaque action) → MembreCouloirRepository/CouloirRepository.
