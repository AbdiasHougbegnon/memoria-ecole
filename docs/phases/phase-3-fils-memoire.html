§ Le besoin

memoria-master-prompt.md demande un regroupement automatique de sessions par thème. Trois réunions sur le même projet, réparties sur plusieurs semaines, doivent se retrouver regroupées toutes seules, avec un nom généré par IA et un résumé qui s'enrichit à chaque nouvelle session — sans que l'utilisateur crée ou nomme quoi que ce soit lui-même.

§ La question centrale : comment décider ?

Le piège déjà découvert en recherche sémantique — les scores de similarité cosinus d'ada-002 sont trop resserrés (0.82 pour du bruit, 0.89 pour un vrai match) pour poser un seuil fiable. Pour la recherche, une erreur de seuil dégrade juste un classement. Pour les fils, elle mélangerait durablement des sujets sans rapport — bien plus grave.

1Filtre gratuitsimilarité cosinus en Java contre tous les fils, garde les 3 plus proches
→
2Décision fiableAzure OpenAI juge le contenu réel des 3 candidats, pas un score
→
3Rejoint ou créerésumé cumulatif fusionné, ou nouveau fil nommé

Stockage : PostgreSQL, comparaison en Java — le nombre de fils reste petit (dizaines, pas millions), pas besoin d'un deuxième index vectoriel Azure AI Search pour ça.

Tous dans com.memoria.core.filmemoire.

Rien n'est lié dans l'autre sens. La table sessions ne sait pas à quel fil elle appartient — c'est FilMemoire qui connaît ses sessions via une simple liste d'identifiants (même patron que segmentsSources pour Resume/CompteRendu).

MEMBER OF interroge directement une @ElementCollection — pas besoin d'une table de jointure séparée juste pour la vérification d'appartenance.

GenerateurFilMemoireAzureOpenAIla décision, avec garde-fou

Prompt strict : « ne rattache une session à un fil que si le sujet est vraiment le même, pas juste vaguement similaire ». Réponse JSON avec filId/nouveauNom/resumeMisAJour.

boolean estUnCandidatConnu = candidats.stream().anyMatch(c -> c.id().equals(id));
return estUnCandidatConnu ? id : null;

Ne fait jamais confiance aveuglément à l'identifiant renvoyé par le modèle — s'il ne correspond à aucun candidat présenté, traité comme "nouveau fil" plutôt que de planter ou rattacher au hasard.

FilMemoireServicele chef d'orchestre

Réutilise le résumé DETAILLE déjà généré (ResumeService.obtenirOuGenererResume) plutôt que de relire la transcription — évite un prompt redondant, et surtout élimine une dépendance d'ordre fragile : résumé et regroupement sont déclenchés par les mêmes événements, sur des threads asynchrones sans garantie d'ordre entre eux.

List<FilMemoire> candidatsTries = filMemoireRepository.findAll().stream()
    .sorted(Comparator.comparingDouble(f -> similariteCosinus(vecteurSession, ...)).reversed())
    .limit(3)
    .toList();

Deux appels d'embedding par session (parfois) : un pour le résumé de la session (trouver les candidats), un second pour le résumé cumulatif final choisi (potentiellement fusionné) — le vecteur stocké doit représenter fidèlement le contenu réel du fil, pas juste la dernière session.

§ Le bug rencontré : @Lob et les Large Objects Postgres

—

500 sur le premier test réel

Symptôme — JpaSystemException: Unable to access lob stream, cause racine : PSQLException: Les Large Objects ne devraient pas être utilisés en mode auto-commit.

@Lob
@Column(name = "embedding")
private byte[] embedding;

Cause — sur PostgreSQL, @Lob sur un byte[] fait choisir à Hibernate le type Large Object (un OID référençant un objet stocké séparément) plutôt qu'une colonne binaire simple. Les Large Objects exigent une vraie transaction explicite — ils plantent en mode auto-commit.

@Column(name = "embedding", columnDefinition = "bytea")
private byte[] embedding;

Correctif — retirer @Lob, mapper directement en bytea. Sans @Lob, Hibernate mappe un byte[] vers bytea par défaut — pas de contrainte transactionnelle. La table existante a dû être supprimée et recréée (le type de colonne ne se convertit pas automatiquement avec ddl-auto=update) — sans risque, données de test uniquement.

Leçon à retenir — ne jamais utiliser @Lob pour un byte[] destiné à PostgreSQL sur ce projet, sauf besoin explicite de fichiers volumineux. Pour un vecteur de quelques kilo-octets, bytea classique suffit et évite ce piège.

§ Limites connues, assumées

  • Fenêtre de course non éliminée à 100% entre les deux déclencheurs d'événement — réduite au minimum, pas verrouillée au niveau transactionnel.
  • Pas de signal de voix — deux sessions avec les mêmes intervenants ne sont pas rapprochées via leur identité vocale, seul le contenu compte. Attendra la reconnaissance de voix récurrente (Phase 3, pas encore construite).
  • Une session appartient à un seul fil, pas de multi-appartenance — choix de simplicité.
  • Pas d'interface pour renommer ou scinder un fil manuellement — purement automatique pour l'instant.

§ Pour reprendre seul

  • Si un futur champ byte[] doit être ajouté à une entité JPA : ne jamais utiliser @Lob sur Postgres pour un simple vecteur — mapper en bytea directement.
  • Nombre de fils candidats soumis à la décision : NOMBRE_CANDIDATS_MAX dans FilMemoireService.java.
  • Prompt de décision (plus strict/permissif) : GenerateurFilMemoireAzureOpenAI.CONSIGNE, aucun autre fichier à toucher.
  • Chemin de bout en bout : événements de fin de session → FilMemoireService → ResumeService + GenerateurEmbeddingPort (recherche) + GenerateurFilMemoirePort → FilMemoireRepository → FilMemoireController → FilsMemoirePage.tsx.
