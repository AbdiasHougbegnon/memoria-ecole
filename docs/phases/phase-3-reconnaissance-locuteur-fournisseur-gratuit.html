§ Le besoin

Suite directe de la première brique (tag phase-3-reconnaissance-locuteur), bloquée sur le retrait d'Azure Speaker Recognition (30/09/2025). Deux familles d'alternatives : d'autres clouds payants (AWS Connect Voice ID, Google SpeakerID) ou des modèles auto-hébergés open-source (pyannote, SpeechBrain, WeSpeaker). Décision explicite de l'utilisateur : pas de fournisseur payant. Direction retenue : auto-hébergé.

§ Les décisions de conception

  • Un service Python séparé, appelé en HTTP — les modèles open-source sont quasi exclusivement Python/PyTorch. Plutôt qu'une bibliothèque Java équivalente (rare, moins mature), un petit service speaker-service/ expose une API HTTP minimale, cohérent avec le reste du projet (Azure via HttpClient brut, jamais de SDK). Le port IdentificateurLocuteurPort ne change pas.
  • SpeechBrain ECAPA-TDNN, pas de fine-tuning — modèle pré-entraîné utilisé tel quel, PyTorch CPU uniquement (pas de GPU nécessaire pour ce volume).
  • Persistance par fichier — chaque profil est un .npy (embedding) sur disque, même réflexe que StockageAudioFichierLocal côté Java. Pas de nouvelle base de données.
  • Le client Azure n'est plus un bean Spring — @Component retiré de IdentificateurLocuteurAzureSpeech, gardé uniquement comme trace documentaire du retrait.

§ Les fichiers

1

speaker-service/ (nouveau, Python)

main.py : POST /profils, DELETE /profils/{id}, POST /identification?profilIds=... (similarité cosinus, confiance dans [0,1]), GET /sante. Dockerfile télécharge le modèle au build. README.md pour le lancement local/Docker.

2

IdentificateurLocuteurSpeechBrain (nouveau, Java)

Implémente IdentificateurLocuteurPort via HttpClient (multipart, même pattern que les clients Azure). Dégradation gracieuse : identifier() renvoie aucunMatch() si injoignable ; enroller()/supprimerProfil() lèvent IdentificationLocuteurException.

§ Limites connues, assumées

  • Un seul processus, pas de scaling horizontal — suffisant pour ce stade du projet.
  • CPU seulement — pas optimisé pour un débit élevé.
  • Aucune authentification entre le backend Java et speaker-service/ — à corriger avant une exposition au-delà de localhost.
  • Seuil de confiance non calibré statistiquement contre ce nouveau modèle (toujours 0.70 par défaut).
  • Toutes les limites de la première brique restent valables — pas de recollement inter-chunks, pas de ciblage de Engagement.responsable.
