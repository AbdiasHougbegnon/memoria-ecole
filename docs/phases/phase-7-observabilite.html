§ Le besoin

Le master prompt : "Prometheus + Grafana + OpenTelemetry (observabilité dès la conception)". La fiche technique de la brique précédente concluait : "Prochaine direction retenue... observabilité minimale, explicitement liée à Docker/Terraform dans le master prompt." État avant cette brique : aucune dépendance micrometer/prometheus/opentelemetry, seule /actuator/health exposée, docker-compose.yml à 4 services. Hors périmètre explicite : métriques de coût par tenant, alerting, observabilité frontend, logs centralisés.

§ Les décisions de conception

  • Micrometer + /actuator/prometheus, zéro code métier — instrumente automatiquement HTTP Spring MVC, JVM, Hikari, Tomcat. percentiles-histogram nécessaire pour p95/p99 via histogram_quantile().
  • Agent Java OpenTelemetry en auto-instrumentation — attaché via -javaagent:, zéro code applicatif. Version épinglée (2.30.0), jamais latest. OTEL_METRICS_EXPORTER=none évite une double émission de métriques.
  • Grafana Tempo, jamais exposé à l'hôte — mode monolithique, stockage local, même doctrine que speaker-service : seuls backend (export) et Grafana (lecture) l'atteignent.
  • /actuator/prometheus suit exactement la doctrine de /actuator/health — permitAll(), protégé par la frontière réseau (nginx ne relaie jamais /actuator/*), pas par l'authentification applicative.
  • Grafana provisionné par fichiers — datasources et dashboard montés en lecture seule, reproductibles, jamais perdus au prochain docker compose down.
  • Dégradation gracieuse pour Tempo — même doctrine que EnvoyeurEmailSmtp/clients Azure : absence de destination = warning de log, jamais de crash.

§ Comment on a vérifié en conditions réelles

Trois bugs ont été découverts pendant la vérification par redémarrage réel de conteneurs — pas anticipés par le plan initial, corrigés dans la même brique :

1

L'agent OTel ne déduit pas gRPC du port 4317

Sans OTEL_EXPORTER_OTLP_PROTOCOL=grpc explicite, le SDK retombe sur http/protobuf et échoue en silence contre le port gRPC de Tempo. Corrigé, vérifié par des traces réelles complètes dans Tempo.

2

nginx met en cache l'IP Docker du backend indéfiniment

proxy_pass statique résout le DNS une seule fois au chargement de la config. Après un redémarrage du backend, nginx tapait sur l'ancienne IP (502). Corrigé avec resolver 127.0.0.11 valid=10s; + variable.

3

Une variable dans proxy_pass casse la réécriture de chemin

Le correctif précédent a introduit un chemin ambigu (403 au lieu de 401). Corrigé avec proxy_pass http://$backend_upstream:8080$request_uri; — $request_uri repasse l'URI d'origine sans ambiguïté. Vérifié robuste sur plusieurs redémarrages successifs.

4

HEALTHCHECK frontend échoue en IPv6, nginx répond pourtant bien

wget http://localhost/ résout d'abord en ::1, or nginx n'écoute qu'en IPv4 (0.0.0.0:80) — conteneur marqué "unhealthy" en continu malgré un trafic réel fonctionnel. Corrigé en utilisant http://127.0.0.1/ explicitement dans le HEALTHCHECK.

§ Limites connues, assumées

  • Pas de métriques de coût par tenant/service — chantier séparé ("Maîtrise des coûts Azure" du master prompt).
  • Pas d'alerting (Alertmanager) — dashboards de consultation uniquement.
  • Pas d'observabilité frontend (Sentry/RUM) — ce lot couvre uniquement le backend.
  • Pas de logs centralisés (Loki) — seulement métriques + traces.
  • Ports 9090/3000 publiés localement — en Azure réel, seul le NSG Terraform contrôle l'accès depuis Internet.
  • API Grafana (curl) non fiable pendant cette session — 403 malgré des logs de provisioning propres ; probablement un contrôle CSRF/origin de Grafana 11.x. Vérification manuelle au navigateur recommandée.

§ Pour reprendre seul

  • Grafana : http://localhost:3000, admin / GF_SECURITY_ADMIN_PASSWORD du .env, dashboard "Memoria Backend" préprovisionné.
  • Prometheus : http://localhost:9090 — debug local uniquement.
  • Tempo : jamais exposé, consultable via Grafana Explore (datasource "Tempo").
  • Prochaine direction possible : qualité (SonarQube/OWASP dependency-check) ou tuteur vocal École — à choisir explicitement.
