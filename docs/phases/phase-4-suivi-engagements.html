§ Le besoin

memoria-master-prompt.md place le suivi des engagements dans la Phase 4 ("Plateforme"), décrit pour la couche Entreprise comme des "decisions, engagements/tasks, deadlines, owners, projects, clients" avec de l'"action-item tracking with human confirmation".

Le compte rendu complet (Phase 2) extrait déjà des actions via Azure OpenAI, mais elles restent de simples lignes de texte sans identité propre, sans statut, sans façon de dire "celle-ci est faite". Cette brique leur donne un vrai cycle de vie — cohérent avec la doctrine du projet : l'IA n'est jamais la source de vérité. Une action extraite reste EN_ATTENTE tant qu'un humain ne l'a pas validée.

Choisie comme première brique de Phase 4 plutôt que l'isolation multi-tenant ou le passage à l'échelle : aucune nouvelle infrastructure requise, et elle prolonge directement un module déjà en place.

§ Les décisions de conception

Comment déclencher la création des engagements ?

Le compte rendu est généré à la demande (bouton cliqué par l'utilisateur), pas automatiquement en fin de session — pour ne pas ajouter un appel Azure OpenAI de plus par défaut (discipline de coûts du projet).

1CompteRenduServicepublie CompteRenduGenereEvent uniquement si nouvellement REUSSI
→
2EngagementServiceecoute l'evenement, totalement decouple (async)
→
3Un Engagement par actionstatut initial toujours EN_ATTENTE

Même patron déjà en place dans le projet (SessionTermineeEvent, ToutesTranscriptionsTermineesEvent consommés par ResumeService/FilMemoireService) — reproduit à l'identique plutôt qu'un couplage direct entre services.

Le cycle de vie : quatre statuts, deux transitions valides

EN_ATTENTE
— confirmer →
CONFIRME
— terminer →
TERMINE
EN_ATTENTE
— rejeter →
REJETE

REJETE et TERMINE sont terminaux, pas de retour en arrière. Ces règles vivent dans l'entité (Engagement.confirmer()/rejeter()/terminer()), qui lève TransitionEngagementInvalideException si l'état ne le permet pas — service et contrôleur n'ont aucune logique de transition à dupliquer.

Traçabilité — pas de nouveau mécanisme : un Engagement porte son sessionId, comme Resume.segmentsSources ou CompteRendu.segmentsSources. Pour remonter à la phrase d'origine : session → compte rendu (déjà lié à ses segmentsSources) → transcription.

§ Les fichiers backend, un par un

CompteRenduGenereEventnouveau, dans entreprise.compterendu 
public record CompteRenduGenereEvent(UUID sessionId) {}

Minimal à dessein — comme les autres événements du projet, il porte juste l'identifiant, chaque écouteur va rechercher lui-même ce dont il a besoin.

CompteRenduServicemodifié — publie l'événement 
CompteRendu sauvegarde = compteRenduRepository.save(compteRendu);
if (statut == StatutCompteRendu.REUSSI) {
    eventPublisher.publishEvent(new CompteRenduGenereEvent(sessionId));
}
return sauvegarde;

Publié uniquement dans la branche qui sauvegarde réellement un nouveau compte rendu — jamais sur une exécution concurrente déjà traitée, jamais sur ECHEC.

Engagemententité JPA — transitions dans le domaine 
public void confirmer() {
    if (statut != StatutEngagement.EN_ATTENTE) {
        throw new TransitionEngagementInvalideException(id, statut, StatutEngagement.CONFIRME);
    }
    changerStatut(StatutEngagement.CONFIRME);
}

Toujours créé avec statut = EN_ATTENTE (un seul constructeur public). responsable ("Intervenant N" ou null) et echeance (texte libre) reprennent exactement les mêmes limites déjà assumées par ActionCompteRendu en Phase 2.

EngagementServicele chef d'orchestre 
@Async @EventListener
public void surCompteRenduGenere(CompteRenduGenereEvent evenement) {
    if (engagementRepository.existsBySessionId(sessionId)) return;
    CompteRendu compteRendu = compteRenduRepository.findBySessionId(sessionId).orElse(null);
    if (compteRendu == null || compteRendu.getStatut() != StatutCompteRendu.REUSSI) return;
    try {
        creerEngagements(sessionId, compteRendu.getActions());
    } catch (Exception e) {
        LOG.warn("Echec de la creation des engagements pour la session {}", sessionId, e);
    }
}

Même structure défensive que FilMemoireService/ResumeService : garde d'idempotence à l'entrée, revérifiée juste avant la sauvegarde. Les actions à description vide sont filtrées avant création — Azure OpenAI peut légitimement renvoyer un tableau actions vide.

§ Dashboard et section session

EngagementsPage.tsx (route /engagements) — dashboard global filtrable par statut, badges colorés, boutons d'action pertinents pour l'état courant. SessionDetailPage.tsx gagne une section "Engagements" sous le compte rendu, incluse dans le même chargement périodique (3s) que le reste de la page — pas de code de rafraîchissement supplémentaire à écrire, le polling déjà en place suffit.

types.ts/api.ts suivent le principe déjà établi : DTO recopiés à la main depuis les réponses Java.

§ Comment on a vérifié en conditions réelles

1

Via l'API, avec un vrai appel Azure OpenAI

Transcription insérée avec deux actions concrètes ("Marie doit envoyer le rapport financier avant vendredi", "Julien doit contacter le fournisseur avant la fin du mois") : Azure OpenAI extrait bien 2 actions distinctes, responsable et échéance corrects.

2

Création automatique confirmée

GET /sessions/{id}/engagements → 2 engagements créés, tous deux EN_ATTENTE, titre de session résolu.

3

Transitions valides et invalides testées explicitement

confirmer → CONFIRME, rejeter → REJETE, terminer sur le CONFIRME → TERMINE. Puis : terminer sur le REJETE → 409, re-confirmer sur le TERMINE → 409, confirmer sur un id inexistant → 404. Dashboard et filtres (?statut=) vérifiés. Aucune erreur en log.

4

Via une vraie session enregistrée à la voix

Test final effectué par l'utilisateur lui-même : phrase lue à voix haute contenant deux engagements du même type, enregistrée normalement, compte rendu généré depuis l'UI — engagements apparus sur la session et sur le dashboard. Confirmé fonctionnel de bout en bout, affichage inclus.

§ Limites connues, assumées

  • Pas de vraie date absolue pour l'échéance — texte libre, même choix que ActionCompteRendu en Phase 2.
  • Pas de vrai nom pour le responsable — "Intervenant N" tant que la reconnaissance de voix récurrente (Phase 3, en attente d'une décision Blob Storage) n'existe pas.
  • Création uniquement à la génération du compte rendu, pas automatique en fin de session — cohérent avec le choix déjà fait pour le compte rendu lui-même.
  • Fenêtre de course non éliminée à 100% entre deux appels concurrents de génération — même compromis déjà accepté ailleurs dans le projet.
  • Pas de retour en arrière — un REJETE ou un TERMINE reste définitif.

§ Pour reprendre seul

  • Nouveau statut ou nouvelle transition : tout se passe dans Engagement.java — service et contrôleur n'ont rien à connaître des règles.
  • Changer le déclencheur de création (par ex. aussi en fin de session) : publier CompteRenduGenereEvent depuis un autre point d'entrée, EngagementService n'a rien à changer.
  • Chemin de bout en bout : bouton "Générer le compte rendu complet" → CompteRenduController → CompteRenduService (génère + publie l'événement) → EngagementService (async) → EngagementRepository → EngagementController → EngagementsPage.tsx / section Engagements de SessionDetailPage.tsx.
