Quitter un couloir soi-même

Un membre non-propriétaire peut désormais quitter un couloir qu'il a rejoint par erreur, sans dépendre du propriétaire. La plus petite des trois briques proposées après la gestion du couloir, choisie pour compléter naturellement ce qui existait déjà.

§ Le besoin

Notée comme limite connue dans la doc de la gestion du couloir (tag phase-5-gestion-couloir) : seul le propriétaire pouvait retirer un membre — un membre ayant rejoint un couloir par erreur (mauvaise classe, mauvais lien) n'avait aucun moyen de partir de lui-même sans passer par le propriétaire.

Choisie comme la plus petite des trois options proposées à l'utilisateur (avec le transfert de propriété et les rappels/notifications côté Entreprise) pour compléter naturellement ce qui existait déjà avant d'attaquer un chantier plus gros.

§ Les décisions de conception

  • Réutiliser l'exception existante — ProprietaireNePeutPasSeRetirerException (déjà utilisée par retirerMembre, → 409) est réutilisée telle quelle pour le propriétaire qui tente de quitter son propre couloir : même règle métier ("un couloir ne peut pas se retrouver sans propriétaire"), qu'il s'agisse d'un retrait par un tiers ou par lui-même. Pas de nouvelle exception pour un cas sémantiquement identique.
  • Idempotent, comme rejoindreCouloir — quitter un couloir dont on n'est pas (ou plus) membre ne lève pas d'erreur ; la requête dérivée ne supprime alors simplement aucune ligne, et renvoie 204 comme dans le cas nominal.

§ Le backend

1

CouloirService.quitterCouloir — nouvelle méthode

@Transactional
public void quitterCouloir(UUID couloirId, UUID utilisateurId) {
    Couloir couloir = obtenirCouloir(couloirId);
    if (utilisateurId.equals(couloir.getProprietaireId())) {
        throw new ProprietaireNePeutPasSeRetirerException(couloirId);
    }
    membreCouloirRepository.deleteByCouloirIdAndUtilisateurId(couloirId, utilisateurId);
}

Pourquoi @Transactional — même raison que retirerMembre/supprimerCouloir : deleteByCouloirIdAndUtilisateurId est une requête dérivée, pas héritée de JpaRepository, donc pas transactionnelle par défaut. Audité récemment (tag précédent) : c'est le seul cas de ce type dans le projet.

2

CouloirController — une route de plus

POST /api/v1/couloirs/{id}/quitter   -> 204

§ Le frontend

CouloirDetailPage.tsx — nouveau calcul estMembreNonProprietaire = !estProprietaire && membres.some(m => m.utilisateurId === utilisateurIdConnecte). Bouton "Quitter le couloir" affiché uniquement dans ce cas, avec confirmation puis redirection vers /couloirs — même schéma que "Supprimer le couloir" côté propriétaire.

§ Limites connues, assumées

  • Aucune notification au propriétaire quand un membre quitte — cohérent avec l'absence générale de système de notification dans le projet à ce stade (chantier Entreprise identifié séparément, pas construit).
  • Pas de conséquence particulière sur les sessions rattachées — elles ne dépendent pas du nombre de membres, seul le propriétaire structure le couloir.

§ Pour reprendre seul

  • Chemin de bout en bout : CouloirDetailPage.tsx (bouton conditionnel sur estMembreNonProprietaire) → quitterCouloir (api.ts) → CouloirController → CouloirService.quitterCouloir (même garde propriétaire que retirerMembre) → MembreCouloirRepository.deleteByCouloirIdAndUtilisateurId.
  • Reste hors périmètre de la série "gestion du couloir" : le transfert de propriété (voir phase-5-gestion-couloir.html, section "pour reprendre seul", pour une esquisse d'implémentation).
