Rappels par email sur les échéances d'engagements

Un bloqueur réel a été trouvé avant d'écrire une ligne de code : ni l'échéance ni le responsable d'un engagement n'étaient exploitables pour programmer un rappel. Ce dossier couvre les deux décisions posées à l'utilisateur, l'architecture retenue, et une vérification avec un vrai envoi SMTP.

§ Le besoin

Après avoir clos la série "gestion du couloir" (École), le chantier suivant côté Entreprise : le master prompt décrit "Rappels contextualisés adressés d'abord à la personne concernée" et une "boucle de responsabilité fermée" comme cœur de la valeur Entreprise. Engagement avait déjà un cycle de vie complet, mais aucun rappel automatique n'existait.

§ Les décisions de conception

  • Échéance — champ dateEcheance structuré, optionnel, saisi manuellement. Rejeté : parser automatiquement le texte libre (contraire à la doctrine "l'IA n'est jamais source de vérité") ; reporter le chantier.
  • Destinataire — rappel envoyé aux participants de la session (créateur + membres du couloir si rattachée). Rejeté pour démarrer : champ "assigné à" dédié (plus juste, plus de friction) ; attendre la reconnaissance de locuteur récurrente (fonctionnalité future).
  • Le port email vit dans le moteur — com.memoria.core.email, pas com.memoria.entreprise : capacité générique, potentiellement utile à l'École aussi (rappel de séance). La logique métier (qui/quand/contenu) reste dans com.memoria.entreprise.engagement.
  • Dégradation gracieuse si SMTP non configuré — même réflexe que TranscripteurAzureSpeech pour Azure : host vide → avertissement au démarrage, aucun crash, envoi silencieusement no-op.
  • Idempotence via deux flags booléens — rappelEcheanceProcheEnvoye/rappelRetardEnvoye, réinitialisés si la date change.

RappelEngagementService — la piece centrale

@Scheduled(cron = "${memoria.rappel.cron}")
public void verifierEcheances() {
    Instant maintenant = Instant.now();
    for (Engagement e : engagementRepository.findByStatutAndDateEcheanceNotNull(StatutEngagement.CONFIRME)) {
        traiterEngagement(e, maintenant);
    }
}

Detail — fenetre "echeance proche" : 24h. Frequence par defaut : toutes les heures, externalisee via memoria.rappel.cron (a permis une verification reelle sans attendre une heure pleine, voir §7). Si aucun destinataire n'est resolu, le rappel n'est pas marque comme envoye -- il pourra se declencher plus tard.

§ Comment on a vérifié en conditions réelles

Un serveur SMTP factice local (smtp-server, npm, port 2525) a été monté pour cette vérification, et memoria.rappel.cron temporairement réglé sur */10 * * * * * au lieu d'attendre une heure pleine — uniquement pour cette session ; la config de production reste horaire et sans hôte SMTP par défaut.

Incident de migration de schéma, trouvé et corrigé pendant la vérification

Au premier redémarrage, ddl-auto=update a échoué : Postgres a refusé la colonne rappel_retard_envoye en NOT NULL sur une table engagements déjà peuplée (ERROR: ... contains null values). Hibernate n'a pas fourni de valeur par défaut pour les lignes existantes. Corrigé manuellement en base (ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT false), puis redémarrage réussi. Pas un bug de code — un rappel que ddl-auto=update n'est pas un outil de migration complet dès qu'une contrainte NOT NULL touche une table déjà peuplée.

§ Limites connues, assumées

  • Le destinataire n'est pas la bonne personne au sens strict — tous les participants reçoivent le rappel, pas spécifiquement le responsable (juste un label de diarization aujourd'hui). Décision assumée, à revisiter avec la reconnaissance de locuteur récurrente.
  • Pas de "boucle fermée" à la complétion — le master prompt décrit aussi une notification à la terminaison ; non construite ici, scope limité aux rappels d'échéance.
  • dateEcheance saisie manuellement — aucun pré-remplissage depuis le texte libre echeance, cohérent avec le refus du parsing automatique.
  • Un seul rappel par type (proche, retard) — pas de rappels répétés en cas de retard prolongé.
  • ddl-auto=update n'est pas une vraie migration — toute future colonne NOT NULL sur une table peuplée demandera la même correction manuelle (pas de Flyway/Liquibase à ce stade).

§ Pour reprendre seul

  • Configuration SMTP réelle : MEMORIA_EMAIL_HOST, MEMORIA_EMAIL_PORT, MEMORIA_EMAIL_USERNAME, MEMORIA_EMAIL_PASSWORD, MEMORIA_EMAIL_EXPEDITEUR. Fréquence : MEMORIA_RAPPEL_CRON.
  • Chemin de bout en bout : EngagementsPage.tsx → planifierEcheanceEngagement (api.ts) → EngagementController → EngagementService.planifierEcheance → Engagement.planifierEcheance → RappelEngagementService.verifierEcheances (cron) → EnvoyeurEmail.envoyer → EnvoyeurEmailSmtp (ou log si non configuré).
  • Pour la "boucle fermée" (non construite) : appeler envoyeurEmail.envoyer(...) depuis EngagementService.terminer, même résolution de destinataires que RappelEngagementService.resoudreDestinataires.
