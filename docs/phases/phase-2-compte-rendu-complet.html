§ Le besoin, et pourquoi valider avant de coder

memoria-master-prompt.md distingue le moteur (transcription, résumé générique) de la couche Entreprise (décisions, engagements, échéances, responsables). Le compte rendu complet est la version Entreprise du résumé : synthèse + décisions actées + actions à faire, avec qui doit la faire et pour quand, quand c'est mentionné.

Avant d'écrire une ligne de code : vérification du principe non négociable de CLAUDE.md — « toute nouvelle capacité répond à un vrai besoin métier validé, pas juste techniquement possible ». Déjà validé en amont (entretiens antérieurs), reconfirmé explicitement par principe avant de concevoir.

§ Décisions de conception

Comment désigner le responsable ?

Le texte contient des repères « Intervenant N » (diarization, Phase 2) — jamais de vrai nom propre. Décision : reprendre « Intervenant N » tel quel, ou laisser vide. Jamais inventer un nom.

Sortie structurée ou texte libre ?

Pour extraire synthèse + décisions + actions avec leur propre structure. Décision : objet JSON avec schéma précis dans le prompt système — même principe déjà utilisé pour les résumés.

§ Le contrat avec Azure OpenAI

Même ressource et même API que pour les résumés — la Responses API, pas l'ancienne Chat Completions (404 systématique sur ce type de ressource AI Foundry, déjà découvert en Phase 2 diarization).

Prompt système envoyé (extrait)

Tu es un assistant qui redige un compte rendu de reunion ou de cours complet et fidele.
La transcription peut contenir des reperes "Intervenant N" : reprends-les tels quels,
n'invente jamais de nom propre.
Reponds UNIQUEMENT avec un objet JSON :
{
  "synthese": "...",
  "decisions": ["decision actee 1", ...],
  "actions": [{"description": "...", "responsable": "Intervenant 2 ou null", "echeance": "... ou null"}]
}
Le champ responsable/echeance doit valoir JSON null (pas la chaine "null") si absent.

Le détail qui compte : préciser explicitement « JSON null, pas la chaîne "null" » — sans ça, un modèle de langage a tendance à écrire littéralement le mot comme texte, ce qui casserait action.path("responsable").isNull() côté Java.

§ Les fichiers backend, un par un

Tous dans com.memoria.entreprise.compterendu — remarque entreprise, pas core : ce vocabulaire (décision, action, responsable) n'existe nulle part dans le moteur.

CompteRenduentité JPA 
@Column(name = "session_id", nullable = false, unique = true)
private UUID sessionId; // un seul compte rendu par session (contrairement a Resume)

@ElementCollection(fetch = FetchType.EAGER) @OrderColumn(name = "position")
private List<String> decisions;
@ElementCollection(fetch = FetchType.EAGER) @OrderColumn(name = "position")
private List<ActionCompteRendu> actions;

Trois @ElementCollection distinctes (trois tables en base), chacune EAGER + @OrderColumn — sans EAGER, Hibernate charge « à la demande », et lire après fermeture de session (sérialisation JSON) plante. Bug déjà rencontré une fois en Phase 1 avec Resume — réflexe systématique depuis.

ActionCompteRendu@Embeddable

description, responsable (« Intervenant N » ou null), echeance — texte libre (« vendredi prochain »), jamais convertie en vraie date : un contresens de conversion automatique serait pire qu'une information laissée telle quelle.

ActionExtraite / CompteRenduGenererecords — DTO du port

ActionExtraite (ce que le port renvoie) et ActionCompteRendu (l'@Embeddable stocké) sont volontairement deux classes séparées qui se ressemblent — ActionExtraite n'a aucune dépendance JPA, un détail de persistance ne fuite jamais jusqu'à l'interface du port. CompteRenduService fait la conversion entre les deux.

CompteRenduServiceorchestration, cache, échec

obtenirOuGenererCompteRendu(sessionId) — généré uniquement à la demande (jamais automatique comme le résumé DETAILLE) : chaque génération coûte un appel Azure OpenAI, en ajouter un systématiquement doublerait le coût par session. Une fois généré (succès ou échec), mis en cache pour toujours — jamais régénéré. enregistrerSiAbsent revérifie une dernière fois avant insertion, contre une course entre deux requêtes simultanées.

GestionnaireExceptionsApimodifié — conflit de nom résolu 
@ExceptionHandler(com.memoria.entreprise.compterendu.AucuneTranscriptionDisponibleException.class)
@ResponseStatus(HttpStatus.CONFLICT)
public void gererAucuneTranscriptionDisponibleCompteRendu() {}

Nom de classe complet plutôt qu'un import : le module resume a déjà sa propre classe AucuneTranscriptionDisponibleException (même nom, package différent). Java interdit d'importer deux classes de même nom simple dans un fichier — le nom complet évite le conflit sans renommer l'une des deux.

§ Le vrai bug d'architecture : Spring Boot ne voyait pas le nouveau package

La partie la plus instructive — se reproduira dès qu'une nouvelle couche produit (École, ou une deuxième fonctionnalité Entreprise) sera ajoutée sans comprendre la cause.

1

Le symptôme

GET /api/v1/sessions/{id}/compte-rendu → 404 — pas une erreur métier, un vrai « cette route n'existe pas », comme si le contrôleur n'était jamais chargé.

2

La cause

Spring Boot scanne à partir du package de la classe @SpringBootApplication et descend dans ses sous-packages. CoreApplication vivait dans com.memoria.core — com.memoria.entreprise.compterendu est un package frère, pas un sous-package. Invisible.

3

Première tentative, qui a cassé autre chose

@SpringBootApplication(scanBasePackages = "com.memoria")
@EntityScan("com.memoria")
@EnableJpaRepositories("com.memoria")

Le 404 disparaît, mais ResumeControllerTest (@WebMvcTest) casse : BeanCreationException sur entityManagerFactory. Ces annotations manuelles contournent le mécanisme d'exclusion automatique de @WebMvcTest, qui force alors le chargement de toute l'infra JPA dans un test qui n'en a pas.

4

Le vrai correctif : déplacer CoreApplication

package com.memoria; // au lieu de com.memoria.core

@SpringBootApplication
@EnableAsync
public class CoreApplication { ... }

Aucune annotation manuelle. Le scan par défaut part de com.memoria et descend naturellement dans core et entreprise. Résultat : les deux problèmes résolus en même temps — 48/48 tests verts, endpoint fonctionnel.

La leçon générale — le point d'entrée @SpringBootApplication doit toujours vivre au niveau du package parent commun à tout ce qu'il doit découvrir. Ajouter des annotations de scan pour « forcer » la visibilité d'un package mal placé est un correctif de surface qui introduit d'autres effets de bord. Corriger l'emplacement du fichier est la vraie solution.

§ Deuxième correction : le délai d'attente Azure OpenAI

—

HttpTimeoutException sur une vraie transcription longue

Symptôme — request timed out sur un cours de plusieurs minutes (60s de délai).

Cause — une sortie structurée (synthèse + décisions + actions) demande plus de texte généré qu'un résumé simple — logiquement plus lent.

Correctif — délai porté à 120s. Précédent identique déjà dans le projet (Azure Speech 30s→90s, Phase 1). Retesté après correctif : succès en 5,7s réelles, listes vides correctement pour un contenu de cours sans décision ni action.

§ Le frontend

Section ajoutée dans SessionDetailPage.tsx — pas une nouvelle page (contrairement à la recherche sémantique, Phase 3, qui a sa page dédiée).

api.ts

export async function obtenirCompteRendu(id) {
  const r = await fetch(`${'{'}BASE{'}'}/${'{'}id{'}'}/compte-rendu`)
  if (r.status === 404 || r.status === 204) return null
  return (await verifierReponse(r)).json()
}

404 et 204 traités comme un simple null — pas une erreur, juste « pas encore de compte rendu », un état normal.

Affichage en 3 états qui s'excluent

{!compteRendu && <button>Generer...</button>}
{compteRendu?.statut === 'ECHEC' && <p>message d'echec</p>}
{compteRendu?.statut === 'REUSSI' && ( /* synthese + listes */ )}

Jamais deux blocs visibles en même temps — conditions mutuellement exclusives.

§ Comment on a vérifié

1

Session avec de vraies décisions/actions

Vérifié via Playwright que synthèse, décisions et actions (bon « Intervenant N », bonne échéance) apparaissaient correctement. Un premier essai de vérification automatique avait échoué à tort en cherchant du texte en MAJUSCULES — la mise en majuscule est du CSS (text-transform), pas le contenu réel du DOM. Erreur du script, pas du produit.

2

Cours de mathématiques (aucune décision réelle)

Vérifié que les listes ressortaient bien vides, sans qu'Azure OpenAI n'invente du contenu pour « remplir » le format. C'est aussi ce test qui a révélé le problème de délai (transcription nettement plus longue).

§ Limites connues, assumées

  • responsable reste « Intervenant N », jamais un vrai nom — attendra la reconnaissance de voix récurrente (Phase 3).
  • echeance reste un texte libre, jamais une vraie date — évite un contresens de conversion automatique.
  • Pas de workflow de confirmation humaine sur les actions extraites — cette brique extrait et affiche ; le suivi de cycle de vie des tâches est prévu en Phase 4.

§ Pour reprendre seul

  • Si un nouvel endpoint répond 404 sans raison apparente après l'ajout d'un package produit : relire la section « le vrai bug » avant de chercher ailleurs — presque toujours le même problème, toujours la même solution (jamais d'annotations de scan manuelles).
  • Pour ajuster le prompt Azure OpenAI : GenerateurCompteRenduAzureOpenAI.CONSIGNE, aucun autre fichier à toucher.
  • Si un délai d'attente réapparaît sur une transcription longue : .timeout(Duration.ofSeconds(120)) dans GenerateurCompteRenduAzureOpenAI — déjà ajusté deux fois dans le projet, signe qu'il faudra un jour le rendre proportionnel à la taille du texte.
